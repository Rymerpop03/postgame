# OWASP ASVS 4.0.3 — V2 Authentication, item by item

BACKEND-PLAN.md §0.3.1 condition 6:

> Phase 5 does not exit until reviewed against OWASP ASVS v4 section V2 (authentication),
> item by item, with each item marked met, not-applicable, or accepted-with-reason. The
> completed checklist is committed.

This is that checklist. Reviewed 2026-08-22 against the Phase 5 implementation.

**On the requirement text.** Requirements are **paraphrased**, not quoted — ASVS is
published under CC BY-SA and reproducing it wholesale here would make this document about
copying rather than about reviewing. The numbering follows ASVS 4.0.3. Anyone using this to
make a decision should read the numbered item in the published standard alongside the
verdict below; where a paraphrase and the standard disagree, the standard is right and this
row needs fixing.

**On the marks.**

| Mark | Meaning |
|---|---|
| **MET** | Implemented and covered by at least one test |
| **PARTIAL** | Implemented for what exists today; the rest is named and scheduled |
| **N/A** | The requirement is about a mechanism Postgame does not have |
| **DEFERRED** | Not met. Belongs to a named later phase, and Phase 5 does not claim it |
| **ACCEPTED** | Not met, deliberately, with the reasoning recorded |

**Level.** Postgame targets **L1 throughout and L2 for credential storage (V2.4)**, since
V2.4 is where a database compromise turns into an account compromise. L3 items are marked
N/A with the level noted; they assume hardware authenticators and a threat model this site
does not have.

Summary across the 57 numbered V2 requirements: **15 MET, 3 PARTIAL, 9 DEFERRED,
1 ACCEPTED, 29 N/A.** The N/A count is high because V2.6 to V2.9 are entirely about
authenticators Postgame does not have — look-up secrets, out-of-band factors, OTP and
cryptographic devices — which is 19 items on its own.

## V2.1 Password Security

| # | Requirement (paraphrased) | Mark | Where / why |
|---|---|---|---|
| 2.1.1 | User-set passwords are at least 12 characters | **MET** | `passwords.MIN_LENGTH = 12`. `test_short_passwords_are_refused`, `test_exactly_the_minimum_is_accepted` |
| 2.1.2 | Passwords of 64 characters or more are permitted | **MET** | `MAX_LENGTH = 256`. The cap exists to bound Argon2 work — an unbounded field lets the caller choose our CPU and memory cost — and 256 is four times the required floor |
| 2.1.3 | Passwords are not truncated; runs of whitespace may be collapsed | **MET** | Nothing truncates or strips. `normalise()` applies NFKC only, and its docstring says why stripping is refused: a leading space is a legitimate password character and removing one changes the secret without saying so |
| 2.1.4 | Any printable Unicode character, including spaces and emoji, is accepted | **MET** | No character class is enforced anywhere. `test_normalisation_is_applied_on_both_sides` covers the non-ASCII path, which is the one that actually breaks in practice |
| 2.1.5 | Users can change their password | **DEFERRED** | Phase 6 — `POST /api/auth/password/change`. Phase 5 ships the session-rotation primitive it needs (`sessions.revoke_all(except_id=...)`) and tests it |
| 2.1.6 | Changing a password requires both the old and the new one | **DEFERRED** | Phase 6, same endpoint |
| 2.1.7 | Passwords are checked against a set of breached passwords | **PARTIAL** | `breached.is_breached`, checked at signup, refusing with an explanation. **The shipped list is not the real corpus** — it is generated by `tools/build_password_list.py` and covers 31,996 entries at or above the 12-character minimum, out of 166,241. `PG_PASSWORD_LIST` points at a real corpus when there is one, and `deployment_warnings()` says so in production. Recorded as partial rather than met because the gap is real |
| 2.1.8 | A password strength meter is offered | **DEFERRED** | Frontend work, and it belongs with the signup form rather than with the API. Phase 5 is backend-only; the API already returns a specific, readable reason for every rejection, which is what a meter would need |
| 2.1.9 | No composition rules are imposed | **MET** | There are none. `test_no_composition_rules` submits an all-lowercase passphrase with no digits or symbols and requires it to be accepted |
| 2.1.10 | No periodic credential rotation is required | **MET** | Nothing expires a password. Forced rotation produces `Spring2026!` and then `Summer2026!` |
| 2.1.11 | Paste, browser password helpers and external managers are permitted | **MET — fixed during this review** | It was not met. Both password fields and both username fields in `js/app.js` carried `autocomplete="off"`, which fights the one habit that most reduces credential reuse and buys nothing: every current browser ignores `off` on credential fields anyway. Now `username`, `current-password`, `new-password` and `name`. The search box keeps `off`, correctly — it is not a credential |
| 2.1.12 | The user can reveal the password temporarily, or see the last character typed | **DEFERRED** | Frontend, with 2.1.8 |

## V2.2 General Authenticator Security

| # | Requirement (paraphrased) | Mark | Where / why |
|---|---|---|---|
| 2.2.1 | Anti-automation controls against credential testing and brute force; no more than 100 failed attempts per hour on one account | **MET** | 5 per 15 minutes per (address, account) and 20 per hour per address — an order of magnitude below the ceiling. `TestEndpointLimits`. **No account lockout**, deliberately: locking on failed attempts lets anyone lock anyone out of their own account, which turns a nuisance into a denial of service. `test_there_is_no_account_lockout` asserts a second client signs in normally while the first is throttled |
| 2.2.2 | Weak authenticators such as SMS are limited to secondary use | **N/A** | There are none. Password only in Phase 5; email is a verification channel in Phase 6, not an authenticator |
| 2.2.3 | The user is notified after changes to authentication details | **DEFERRED** | Phase 6, with transactional email. Every such event already writes to `audit_log`, which is the record the notification will be generated from |
| 2.2.4 | Impersonation resistance against phishing (L3) | **N/A** | L3. Requires WebAuthn or similar |
| 2.2.5 | Verifier and authenticator communicate over a mutually authenticated channel (L3) | **N/A** | L3 |
| 2.2.6 | Replay resistance (L3) | **N/A** | L3. Sessions are single-use-per-request bearer cookies over TLS, which is the L1/L2 expectation |
| 2.2.7 | Intent to authenticate is demonstrated (L3) | **N/A** | L3 |

## V2.4 Credential Storage — target level L2

| # | Requirement (paraphrased) | Mark | Where / why |
|---|---|---|---|
| 2.4.1 | Passwords are stored in a form resistant to offline attack — approved KDF with salt | **MET** | Argon2id via `argon2-cffi`, m=64 MiB, t=5, p=1, measured at 268 ms on the development machine. `test_the_hash_is_argon2id_and_carries_its_parameters` |
| 2.4.2 | The salt is at least 32 bits and unique per credential | **MET** | `salt_len=16` — 128 bits, four times the requirement, generated per hash by argon2-cffi. `test_the_same_password_hashes_differently_every_time` |
| 2.4.3 | PBKDF2 uses at least 100,000 iterations | **N/A** | PBKDF2 is not used |
| 2.4.4 | bcrypt uses a cost factor of at least 10 | **N/A** | bcrypt is not used |
| 2.4.5 | An additional iteration of a KDF is performed with a secret known only to the verifier (a "pepper") | **ACCEPTED** | Not implemented. A pepper genuinely helps in the one case it is designed for — the database leaks and the application host does not — and this deployment is one machine, where that separation is thin. It is also awkward to rotate: changing it invalidates every stored hash at once, so doing it properly needs a two-key verification window on top of the rehash-on-login machinery. Recorded for the Phase 16 hardening pass, where it can be introduced alongside a real secret store rather than as an environment variable sitting next to the database URL |

Note on **rehash on login** (not a numbered requirement, but the thing that makes 2.4.1
maintainable): `Hasher.needs_rehash` runs after a successful verification and the hash is
upgraded in place, so raising the parameters is a deploy rather than a migration and nobody
is asked to reset anything. `test_raising_the_cost_upgrades_the_stored_hash_at_next_login`.

## V2.10 Service Authentication

| # | Requirement (paraphrased) | Mark | Where / why |
|---|---|---|---|
| 2.10.1 | Intra-service authentication does not rely on unchanging shared credentials such as default passwords or API keys | **PARTIAL** | The only intra-service credential is the database password, held in `PG_DATABASE_URL`. ## Beyond condition 6: V3 Session Management in brief

Not required by §0.3.1, which names V2. Included because Phase 5 built the session layer as
well, and reviewing the authentication half without the session half would be a strange
place to stop.

| # | Requirement (paraphrased) | Mark | Where |
|---|---|---|---|
| 3.1.1 | Session tokens never appear in URL parameters | **MET** | Cookie only. Nothing in the API accepts a token as a query parameter |
| 3.2.1 | A new session token is generated on authentication | **MET** | `sessions.create` inserts a fresh row every time and login revokes whatever was presented. §0.3.1 condition 4; `test_login_issues_a_new_session_and_kills_the_old_one` |
| 3.2.2 | Session tokens carry at least 64 bits of entropy | **MET** | 256 bits from `secrets.token_bytes(32)`. `test_tokens_are_256_bits_of_urlsafe_base64` |
| 3.2.3 | Tokens are stored using a secure method | **MET** | SHA-256 only; the raw value exists in the process for the length of one request. `test_the_raw_token_appears_nowhere_in_the_database` scans every text and jsonb column in the schema, not just `sessions` |
| 3.2.4 | Tokens are generated with an approved CSPRNG | **MET** | `secrets`, not `random` |
| 3.3.1 | Logout terminates the session | **MET** | `revoked_at` is set server-side; clearing the cookie is a courtesy. `test_a_revoked_session_no_longer_authenticates` replays the cookie after logout |
| 3.3.2 | Idle timeout, re-authentication after inactivity | **MET** | 14 days idle, 90 days absolute, earlier wins. `TestSessionLifetime` |
| 3.3.3 | Sessions can be terminated from an administrative interface | **PARTIAL** | `POST /api/auth/logout-all` covers the user's own sessions. A moderator-facing view is Phase 13 |
| 3.3.4 | Users can view and terminate active sessions | **DEFERRED** | Phase 6 — `GET /api/auth/sessions` |
| 3.4.1 | Cookie-based tokens set `Secure` | **MET** | Everywhere except `local`, where the name differs too so a local cookie cannot be mistaken for a real one |
| 3.4.2 | Cookie-based tokens set `HttpOnly` | **MET** | `sessions.cookie_kwargs` |
| 3.4.3 | Cookie-based tokens set `SameSite` | **MET** | `Lax`. `Strict` was rejected: it drops the cookie on any inbound link, so following a shared link would show you signed out |
| 3.4.4 | Cookie-based tokens use the `__Host-` prefix | **MET** | `__Host-pg_session` in staging and production. `test_real_environments_use_the_host_prefix` |
| 3.4.5 | Path is set to the most precise value possible | **MET** | `/` — required by `__Host-`, and correct here since the whole site is one origin |
| 3.5.x | Token-based session management (JWT, API keys) | **N/A** | Decision 0.4: opaque server-side sessions, no JWTs |

CSRF (V4.2.2 in ASVS terms) is covered in three layers — `SameSite=Lax`, a mandatory
`Origin` match where a missing header is a rejection, and a per-session token derived by
HMAC from the session token. `app/security/csrf.py`, `tests/test_sessions_and_csrf.py`.

## What this review changed

Four things were found while working through the list rather than while writing the code:

1. **2.1.11 was a real defect, and only a checklist would have found it.** Every password
   and username field on the sign-in and sign-up forms carried `autocomplete="off"`. No test
   would ever have caught that, because nothing is broken — the forms work perfectly, and
   they quietly discourage password managers, which is the opposite of what a site with
   passwords should do. Fixed in `js/app.js`; assets are at `?v=33`.
2. **2.1.7 is partial, not met.** The first draft of this checklist said MET. It is not: the
   shipped list is generated, not the real corpus. Writing "MET" there would have been the
   exact failure this project keeps rediscovering — a control that reports success while
   covering less than it claims.
3. **2.10.1 and 2.10.3 are partial.** Environment variables are the normal shape for a
   deployment this size and they are still weaker than a secret store. Naming them here
   means Phase 15 inherits a specific task rather than a good intention.
4. **2.4.5 needed a decision, not a shrug.** "We don't use a pepper" is not a verdict. The
   verdict is that the rotation cost is real, the benefit is small on a single-host
   deployment, and it belongs with Phase 16's secret-store work.
